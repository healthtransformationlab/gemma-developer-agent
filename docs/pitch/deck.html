In fifteen days, one person working with a cloud coding agent took a health-data repository from nothing to 960 commits and 2,269 tests, without typing code. This deck asks what a small model, one that runs on a single GPU, can take out of that loop. The answer comes with a task set anyone can use: 93 real changes from that repository, each verified by the competition's own evaluator. Every patient record in the repository is synthetic. The problem

Coding benchmarks draw on a few popular libraries. Data work fails differently.

  • SWE-bench draws on twelve popular Python libraries; the competition's development set, on four.
  • In a data repository the costly defect is silent: a pipeline finishes and a number in its table is wrong.
  • An agent-built repository can leave an unusually complete record: an issue, a pull request and a review for each change.

The competition asks whether a model that fits on one accelerator can do the work of the large cloud models behind today's best coding agents. Its tasks, like SWE-bench's, come from a handful of popular libraries. Two kinds of repository are scarce in such sets. In a data repository the costly defect is silent: nothing crashes, and a number in a table is wrong. And a repository built by an agent, under rules that require an issue, a pull request and a review for every change, leaves a record that can be mined. This repository is both. Of its 960 commits, 775 are marked as agent-authored, and it held 2,269 tests on November 8.

Source: the paper, Sections 4 and 5

The tasks are made the way the competition makes its own: every merged change whose diff touches both code and tests is a candidate. Of 197 merged changes, 116 are candidates. One was withdrawn, one failed a gate and one was withheld for unlicensed third-party files, leaving 113, and the competition's own evaluator verifies 93 of those: the published set. On them it resolves every reference patch and no empty patch. A local harness, which anyone can run, gives the same verdict as the evaluator on all 48 of the model's patches that were compared. Each task comes with a snapshot of the repository, a code graph, embeddings, and a label saying whether its statement came from an issue, a pull request or a commit message.

Left on its own on two free T4 GPUs, taking the cheapest tasks first, Gemma 4 E4B resolved 5 of the 48 tasks it ran, all of them small. Under the competition's evaluator it resolved 3 of 23 of the competition's own development tasks. Then came an experiment whose plan was fixed before any result: all 93 tasks on one A100, three ways. As published, the model resolved 4. With graph retrieval done for it, 6. With a failing test's report, 4. Neither added context differs detectably from the baseline, and a difference is not ruled out either: at 4 of 93 only a large effect could show. Retrieval's two extra fixes do not establish a reliable improvement. The report uses the hidden test, so it is not a benchmark condition.

The core split is the 17 tasks whose statements say what their tests check, by an AI screen of all 93. Finding is not fixing: where retrieval listed a function the fix edits (41 tasks), 5 of the core split's 7 were resolved in some run and none of the other 34.

Described, not testedThe second comparison was made after the runs. Source: the paper, Section 6

This is the result to take away. An AI screen asked of every task whether its statement says what its tests check. Seventeen of the 93 pass: the core split. The other 76 are real statements that leave out something their tests need, such as a name or a message. Over the five Colab runs, 8 of the 17 core-split tasks were resolved at least once, against 1 of the other 76. Counting every task in every run, that is 26 of 85 against 1 of 380. And finding is not fixing: in the 41 tasks where retrieval listed a function the fix edits, 5 of the core split's 7 were resolved in some run and none of the other 34. So valid tasks whose fix the graph found, but whose statements leave out what their tests need, measured little for this model. These are descriptions, not tests, and the second comparison was made after the runs. A person checked 42 of the screen's verdicts, in summary.

What it means: the model's own calls are where the time goes, not the graph tools, and the core-split tasks are where an hour of this model bought the most.

Source: the paper, Section 6, "Time, GPUs and cost". The prices are rental estimates, not money spent

The runs kept OpenTelemetry spans: names, counts and seconds, never prompts or replies. In the three Kaggle arms, 66 to 83 percent of a task's time was model calls and 14 to 15 percent was context compaction, which is the harness summarising older turns. The graph tools took under 0.1 percent. Forty-five of 207 runs ended when a prompt passed the model's context window. A fix took 1.9 GPU-hours with graph retrieval and 1.8 with the report, on four L4s: about 1.59 and 1.50 US dollars at a median rental price, though Kaggle's GPUs were free. On the T4 baseline, the 13 core-split tasks it ran took 17 percent of its 9.0 agent-hours and gave 4 of its 5 fixes: 0.38 hours a fix against 1.80 overall.

Drill-down · limits

What this does not show

One new repository, compared with the competition's development set.

No cloud baseline. The cloud agent that made these changes, with a person in the loop, was not rerun on the statements alone.

A small experiment. At a baseline of 4 of 93 only a large effect could show.

No leaderboard score. Every run under the competition's evaluator used 5 minutes and 40 tool calls, not 60 and 100, once per arm and machine.

AI screens. A person checked 42 verdicts, the core split's 17 among them, in summary and after seeing the AI's; 51 have AI ratings only.

Prompted repair. Each task comes with a failing test: noticing a silent defect unprompted is not measured.

Read the results as: what one small model did on one repository's tasks, with the screen's verdicts checked by one person in part.

Source: the paper, Section 7

Six limits, all in the paper. One repository, set beside the competition's development set. No cloud baseline: the cloud agent that made these changes with a person in the loop was not rerun on the statements alone, so the title's question is answered for the small model only. A small experiment: at 4 of 93 only a large effect could show. No leaderboard score: the runs used 5 minutes and 40 tool calls where the competition allows 60 and 100. The screens are an AI's: a person checked 42 verdicts in summary, after seeing the AI's, and 51 have AI ratings only. And every task comes with a failing test, so noticing a silent defect unprompted is not measured.

Drill-down · evidence you can check

How each number is kept honest

A source for every number. paper/sources.md has a row for each figure in the paper, naming the file it came from, and keeps the rows of text that was cut.

A plan before the results. The experiment's plan was hashed before any result, and each addendum before its run started (source repository, issues 674 and 687).

Checked on every change. In CI, paper/check_rules.py checks the paper against the competition's rules, and docs/build_decks.py checks this deck's numbers against the paper.

What went wrong is in the paper. Colab's network was open to the agent: 3 of the five runs' 687 commands ran an installer, in tasks no run resolved, and none left its workspace.

Not a result: anything from a dry run or a sample is labelled as one, and the unplanned second session is described beside the registered one, never added to it.

Sources: paper/sources.md, paper/rules_check.md and the paper, Section 6

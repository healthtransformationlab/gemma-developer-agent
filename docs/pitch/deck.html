Can a small local agent

redo a cloud agent's work?

A cloud AI agent built a health-data code project. We turned 93 of its real changes into test tasks and asked a small model, Gemma 4 E4B, to make them again.

Health Transformation Lab · Evidence you can check

John Bowyer · personal project, not affiliated with any organization

In fifteen days, one person working with a cloud coding agent took a health-data repository from nothing to 960 commits and 2,269 tests, without typing code. This deck asks what a small model, one that runs on a single GPU, can take out of that loop. The answer comes with a task set anyone can use: 93 real changes from that repository, each verified by the competition's own evaluator, which is its scoring program. Every patient record in the repository is synthetic. This is a personal project, not any organization's plan.

The problem

Tests for AI coding agents use a few popular libraries. Health-data code fails in a different way.

  • The best-known test, SWE-bench, draws on twelve popular Python libraries. The competition's development set draws on four.
  • In a data project the costly mistake is silent: the pipeline finishes and a number in its table is wrong.
  • A project built by an AI agent can leave an unusually complete record: an issue, a pull request and a review for each change.

Source: the paper, Sections 1 and 3

The competition asks whether a model that fits on one accelerator can do the work of the large cloud models behind today's best coding agents. Its tasks, like SWE-bench's, come from a handful of popular libraries. Two kinds of repository are scarce in such sets. In a data repository the costly defect is silent: nothing crashes, and a number in a table is wrong. And a repository built by an agent, under rules that require an issue, a pull request and a review for every change, leaves a record that can be mined. This repository is both. Of its 960 commits, 775 are marked as agent-authored, and it held 2,269 tests on November 8.

The scoring works. Given the real fix, the scoring program (the evaluator) passes 93 of 93 tasks. Given no change, it passes 0 of 93.

Anyone can run it. Our open test harness gave the scoring program's verdict on every answer compared: 25 of 25 and 23 of 23.

Each task comes with a copy of the code, a map of the code (a graph), and where its description came from: an issue, a pull request or a commit message.

Source: the paper, Sections 4 and 5

The tasks are made the way the competition makes its own: every merged change whose diff touches both code and tests is a candidate. Of the 197 changes merged by October 29, 2026, 116 are candidates. One was withdrawn, one failed a gate and one was withheld for unlicensed third-party files, leaving 113, and the competition's own evaluator verifies 93 of those: the published set. On them it resolves every reference patch and no empty patch. A local harness, which anyone can run, gives the same verdict as the evaluator on all 48 of the model's patches that were compared. Each task comes with a snapshot of the repository, a code graph, embeddings, and a label saying whether its statement came from an issue, a pull request or a commit message.

Left on its own on two free T4 GPUs, taking the cheapest tasks first, Gemma 4 E4B resolved 5 of the 48 tasks it ran, all of them small. Under the competition's evaluator, on four L4 GPUs, it resolved 3 of the 23 development tasks of the competition's own that a Kaggle notebook can verify. Then came an experiment registered in advance. Its plan was fixed before any result; Kaggle could not finish it, so all three arms ran again on one A100, under additions to the plan that were fixed before each run started: all 93 tasks, three ways. As published, the model resolved 4. With graph retrieval done for it, which hands it a list of code to look at, 6. With a failing test's report, 4. Neither added context differs detectably from the baseline, and a difference is not ruled out either: at 4 of 93 only a large effect could show. Retrieval's two extra fixes do not establish a reliable improvement. The report uses the hidden test, so it is not a benchmark condition.

The main finding

The model fixed 8 of the 17 clearly described tasks, and only 1 of the other 76

"Clearly described" means the task's description says what its tests check. An AI made that check on all 93 tasks, and a person checked 42 of its verdicts.

Being pointed at the right code was not enough. In 41 tasks the search listed a function the fix changes. Of the 7 clearly described ones, 5 were fixed in some run. Of the other 34, none.

Described, not tested

Counts of what happened, with no statistical test; the second comparison was made after the runs. The paper calls the 17 the core split (Section 6).

This is the result to take away. An AI screen asked of every task whether its statement, the task's description, says what its tests check. Seventeen of the 93 pass: the paper calls them the core split. The other 76 are real statements that leave out something their tests need, such as a name or a message. Over the five Colab runs, 8 of the 17 core-split tasks were resolved at least once, against 1 of the other 76. Counting every task in every run, that is 26 of 85 against 1 of 380. And finding is not fixing: in the 41 tasks where retrieval listed a function the fix edits, 5 of the core split's 7 were resolved in some run and none of the other 34. So valid tasks whose fix the graph found, but whose statements leave out what their tests need, measured little for this model. These are descriptions, not tests, and the second comparison was made after the runs. A person checked 42 of the screen's verdicts, in summary.

Hours of agent time for each fix, on the T4 baseline

0.38 vs 1.80

0.38 on the 13 clearly described tasks it ran, against 1.80 over all 48. Those 13 took 17% of its 9.0 agent-hours and gave 4 of its 5 fixes.

What it means: the time goes to the model's own calls, not to the graph tools, and an hour spent on clearly described tasks bought the most fixes.

Source: the paper, Section 6, "Time, GPUs and cost". The prices are rental estimates, not money spent

Drill-down · limits

What this does not show

Only one new code project, set beside the competition's development set.

No comparison with the cloud agent. The agent that made these changes, with a person in the loop, was not rerun on the task descriptions alone.

A small experiment. With 4 of 93 tasks fixed as the starting point, only a large effect could show.

Not a leaderboard score. Every run under the competition's scoring program had 5 minutes and 40 tool calls a task, not the 60 and 100 allowed.

An AI checked the descriptions. A person checked 42 of its verdicts, the 17 clearly described tasks among them, in summary and after seeing the AI's; 51 have AI ratings only.

The model was told something was wrong. Each task comes with a failing test: noticing a silent defect unprompted is not measured.

Read the results as: what one small model did on one project's tasks, with the AI's verdicts checked by one person in part.

Source: the paper, Section 7

Six limits, all in the paper. One repository, set beside the competition's development set. No cloud baseline: the cloud agent that made these changes with a person in the loop was not rerun on the statements alone, so the title's question is answered for the small model only. A small experiment: at 4 of 93 only a large effect could show. No leaderboard score: the runs used 5 minutes and 40 tool calls where the competition allows 60 and 100. The screens are an AI's: a person checked 42 verdicts in summary, after seeing the AI's, and 51 have AI ratings only. How you can check every number

A source for every number. paper/sources.md has a row for each figure in the paper, naming the file it came from, and keeps the rows of text that was cut.

A plan before the results. The experiment's plan was fixed and fingerprinted (hashed) before any result, and each addition to it before its run started (source repository, issues 674 and 687).

Checked on every change. One script checks the paper against the competition's rules, and another checks that every number in this deck appears in the paper or the README.

What went wrong is in the paper. On Colab the network was open to the agent: 3 of the five runs' 687 commands ran an installer, in tasks no run fixed, and none left its workspace.

Not a result: anything from a dry run or a sample is labelled as one, and the unplanned second session is described beside the planned experiment and kept out of its tests. A count that covers both says five runs.
